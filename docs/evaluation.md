# Validation and evidence boundaries

Local execution on CPython 3.12, Linux used `pytest -q`, Ruff, real SQLite imports and the
actual supplied policy PDF. The initial suite had 6 failures and 82 passes; investigation
identified incorrect product IDs in test expectations and an overly restrictive assertion
about literal search tokens. Those test assumptions were corrected against the CSV records.
The next full run passed 88 tests with 0 failures. After a monetary-formatting regression
test was added, the final local suite passed 89 tests with 0 failures. The exact dependency
lock installed successfully into a second, initially empty Python 3.12 virtual environment;
data loading and all 89 tests passed there as well. Streamlit also started on loopback and
its HTTP health endpoint returned `ok`; that temporary server was then stopped.

Tests exercise CSV schema/type/foreign-key constraints, atomic failure recovery, historical
totals, exact cents, filters, availability lifecycle, active campaign calculation, PIX
non-stacking, installment rounding, customer verification and cross-account denial,
policy retrieval and page boundaries, return conditions, malformed inputs, unknown tools,
read-only SQLite, scripted model tool calls, failed grounding, provider errors and bounded
multi-turn memory. Streamlit AppTest submits real chat inputs and verifies a follow-up,
identity verification, logout, and conversation clearing. It is an application-level UI
test, not a pixel-rendering or external-browser accessibility audit.

The OpenAI SDK adapter is tested through `httpx.MockTransport`, including request schema,
tool serialization and error handling. That validates the local SDK boundary, not the
remote model or the availability of API access. Injection tests demonstrate that extra
identity parameters and invented tools are rejected even if the model requests them;
they do not prove universal resistance to adversarial language or all response hallucinations.

`python scripts/evaluate_retrieval.py` executed a 12-query diagnostic using author-assigned
expected sections. Expected-section hit@3 was 9/12 (75%) for literal token overlap,
9/12 (75%) for a simple TF-IDF cosine baseline, and 12/12 (100%) for BM25 with bilingual
aliases and policy cross-references. For this metric only the first three primary results
are counted; appended dependencies do not increase the measured score. The baseline
uses the same section corpus and term counts with title weighting. These figures describe
different retrieval packages (normalization/expansion/ranking together), not an isolated
ablation proving BM25 alone is better than TF-IDF.

This is a tiny, in-sample diagnostic. Queries and aliases were developed together. It does
not estimate unseen-query accuracy, full context precision/recall, answer faithfulness or
model tool-selection accuracy. Embedding-based retrieval was compared conceptually for
semantic recall, costs, runtime dependencies and operational complexity; it was not run.
There is no empirical claim that lexical retrieval outperforms embeddings.

Five Markdown conversations were generated by `scripts/generate_examples.py` by running
the real Agent/Tools/SQLite/PDF pipeline with the deterministic offline provider. Outputs
are captured from execution, not manually invented dialogue. The examples explicitly say
that no LLM or live store service was invoked. The offline provider supports only a small
set of demonstration intents and should not be used as evidence of open-ended LLM ability.

## Developer-reported manual API validation

Rafael de Matos Abe confirmed that he manually ran the agent in **IA via API** mode with
a real OpenAI API key and obtained satisfactory operation. This records the developer's
confirmation, not a run performed or independently observed by the coding assistant.
No specific prompts, conversation scenarios, transcripts, model/version details or quantitative
results were supplied. No scenario-specific pass counts, latency, accuracy or coverage claims
can be inferred from that confirmation.

This manual validation is distinct from the offline automated suite and the five deterministic
example conversations above. The examples remain offline transcripts; they have not been
relabeled as evidence of the manual API run. A satisfactory manual run does not establish a
systematic real-model benchmark or comprehensive human review of code and generated answers.

During the initial assistant-led implementation, no `OPENAI_API_KEY` was available for the
scripted smoke check: `python scripts/smoke_openai.py` reported NOT RUN and exited 2 without
calling a paid API. That historical result does not contradict the subsequent developer-reported
manual validation. There is no report that the developer ran this particular smoke script.
With a key configured, the script runs three small real-model turns, prints their answers/tool
traces, and returns a failing exit code on missing expected tools or errors. It deliberately
uses only sanitized data. It remains an optional reproducible check; its three scenarios must
not be attributed to the developer's manual validation without execution evidence.
